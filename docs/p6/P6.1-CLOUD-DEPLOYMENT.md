# P6.1 — Managed Cloud Deployment (Railway + AWS)

Production-ready deployment for **Railway** and **AWS**, from the same images. No production
credentials here — secrets are set in each platform's secret store. Money automation stays OFF.

## Service decomposition (both platforms)

| Component                          | Image / source           | Scale                     | Notes                                                                 |
| ---------------------------------- | ------------------------ | ------------------------- | --------------------------------------------------------------------- |
| **API**                            | `apps/api/Dockerfile`    | ≥2                        | stateless; `/api/health` (live), `/api/ready` (ready), `/api/metrics` |
| **Worker**                         | `apps/worker/Dockerfile` | ≥2                        | lease-based; `:4100/health`, `:4100/ready`, `:4100/metrics`           |
| **PostgreSQL**                     | managed                  | 1 primary (+replica prod) | authoritative store + outbox                                          |
| **Redis**                          | managed                  | 1 per env                 | locks + BullMQ + cache (env-namespaced, P6.2)                         |
| **Object storage**                 | S3 / Railway volume      | —                         | tickets/QR/assets; versioning on                                      |
| **Web (customer/organizer/admin)** | per-app Dockerfile       | ≥1                        | Next.js; `NEXT_PUBLIC_API_URL` at build                               |

Migrations run as a **one-shot release step** (`prisma migrate deploy`) before API/worker boot.
Additive-only migrations keep the prior image compatible → safe rollback.

## Environment variables (per environment; set as platform secrets)

**Required:** `APP_ENV` (LOCAL/DEV/QA/UAT/STAGING/PRODUCTION), `DATABASE_URL`, `REDIS_URL`,
`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `QR_SIGNING_SECRET`, `PAYMENT_WEBHOOK_SECRET`,
`NEXT_PUBLIC_API_URL`, `CORS_ORIGINS`. **Payments (per env):** `PAYMENT_PROVIDER_NAME`,
`STRIPE_*` / `RAZORPAY_*` (test in staging, live in prod), `*_MODE`. **Storage/email:** `S3_*` /
`SMTP_*`. See `.env.example`. `APP_ENV` drives startup validation, payment-env resolution, and Redis
namespacing — **set it correctly per environment**.

### Feature flags (P6 policy — safe defaults; do not weaken)

`BOOKING_ORCHESTRATOR_MODE=shadow`, provider-confirmation / allocated-inventory / compensation-
execution / auto-provider-cancel / auto-void / **auto-refund** = `false`,
`BOOKING_REFUND_POLICY_MODE=MANUAL_ONLY`. Startup validation **rejects** money automation +
mock providers when `APP_ENV=PRODUCTION` — do not override.

## Railway deployment plan

One Railway **project** with two **environments** (`staging`, `production`). Each environment has
its own managed PostgreSQL + Redis plugins → **Redis is never shared across environments** (and
P6.2 namespacing is defence-in-depth).

**Services per environment (Dockerfile-based, so they scale/fail independently):**

1. **api** — `railway.json` (root) → `apps/api/Dockerfile`, start `prisma migrate deploy && node apps/api/dist/main.js`, healthcheck `/api/health`, 2 replicas.
2. **worker** — `apps/worker/Dockerfile`, start `node apps/worker/dist/main.js`, healthcheck `:4100/health`, 2 replicas. **No migrate** (api's release does it).
3. **customer-web / organizer-web / admin-web** — per-app Dockerfile, `NEXT_PUBLIC_API_URL` build arg.
4. **PostgreSQL** + **Redis** — Railway plugins.

**Promotion flow:** deploy to `staging` → run P6.2/6.5/6.6 gates → promote the same image tag to
`production` (a manual, approved step). Variables per environment; secrets via Railway variables,
never committed. `Procfile` is the buildpack fallback if not using Dockerfiles.

**Steps (CLI, when authenticated):**

```bash
railway login && railway link                       # select project
railway environment staging
railway add --plugin postgresql && railway add --plugin redis
railway up --service api                             # repeat: worker, *-web
railway variables set APP_ENV=STAGING PAYMENT_PROVIDER_NAME=mock ...   # per service
# promote: railway environment production; set live secrets; deploy same tag; manual approve
```

**Blocked until:** authenticated Railway access + owner approval. No resources created here.

## AWS deployment plan

**Reference topology (ECS Fargate — lowest ops overhead for this workload):**

```
Route 53 → ACM (TLS) → ALB
   ├── target group: api  (ECS Fargate service, 2+ tasks, /api/health)
   └── target group: web  (customer/organizer/admin services)
ECS Fargate service: worker (2+ tasks, no ALB; /health via container check)
RDS PostgreSQL (Multi-AZ, automated backups + PITR)   ← authoritative
ElastiCache Redis (per-env, cluster-mode off or Sentinel)  ← locks/queues/cache
S3 (tickets/assets, versioning + lifecycle) + CloudFront
ECR (api/worker/web images, pushed by CI)
Secrets Manager / SSM Parameter Store (all secrets + DATABASE_URL/REDIS_URL)
CloudWatch (logs) + Managed Prometheus/Grafana or self-hosted (P6.6)
```

**Isolation:** one VPC per environment (or separate subnets + security groups); **separate
ElastiCache per environment** (staging never shares production Redis; app namespacing is
defence-in-depth). RDS in private subnets; ALB is the only public ingress; ECS tasks in private
subnets with NAT for egress.

**Deploy sequence:**

1. CI builds + pushes `api`/`worker`/`web` images to **ECR** (see P6.3).
2. Run migrations as a one-shot ECS task (`prisma migrate deploy`) gated before service update.
3. Update ECS services (rolling, min-healthy 100%, health-check grace 30s).
4. Rollback = redeploy the previous task-definition revision (images are immutable per tag).

**Secrets:** injected from Secrets Manager/SSM as task-definition secrets — never baked into images
or task envs in plaintext. `PAYMENT_*` live keys only in the production account.

**Blocked until:** authenticated AWS access + owner approval. This document is the executable plan;
no infrastructure is provisioned here. IaC (Terraform/CDK) is a follow-up once the account exists.

## Health & readiness (wire platform probes to these)

- **Liveness:** API `GET /api/health`, worker `GET :4100/health` (process up).
- **Readiness:** API `GET /api/ready`, worker `GET :4100/ready` (DB + Redis reachable → gate traffic/rollout).
- **Metrics:** API `GET /api/metrics`, worker `GET :4100/metrics` (Prometheus scrape).
