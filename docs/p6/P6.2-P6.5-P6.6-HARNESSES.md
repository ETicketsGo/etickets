## P6.2 — Real payment-provider sandbox validation

**Gate: PENDING — requires Stripe/Razorpay TEST credentials in `.env.staging`.** Mock-only proof is
**insufficient** to enable auto-refund (per P6.3).

### Runnable harness

`scripts/payments/sandbox-validate.mjs` (to be run against the staging API with sandbox keys) drives,
per provider, the required matrix and asserts each outcome:

**Stripe:** payment create → success → failed-card → **duplicate webhook** (idempotent) → refund →
refund-response-lost recovery → webhook signature (valid + tampered rejected) → idempotency-key reuse →
currency routing (USD→Stripe) → Connect transfer/settlement where applicable.

**Razorpay:** order create → success → failed → **duplicate webhook** → full refund → **async refund
state** → refund status recovery → signature (valid + tampered) → idempotency → INR routing.

## P6.5 — Load & flash-sale testing

**Gate: PENDING live run — harness provided; needs the staging stack.** Do **not** claim IPL-scale
from local runs.

### Harness

`scripts/load/booking-load.js` (k6). Scenarios staged: warm-up → normal → ramp → **flash-sale spike**
→ sustained peak → recovery. Two profiles run **separately**:

- **Read-heavy:** movie/theatre/show listing, seat-map reads, availability checks.
- **Booking-heavy:** initiate → lock acquire → payment initiate → status poll.

```bash
# k6 (install separately); BASE_URL points at the staging LB
BASE_URL=https://staging.eticketsgo... k6 run scripts/load/booking-load.js --vus 200 --stage ...
```

### Measure

RPS · p50/p95/p99 latency · error rate · DB CPU/connections · Redis CPU/mem/cmd-latency · queue depth ·
outbox backlog · worker throughput · lock contention (`etg_inventory_lock_contention_total`) · booking
success rate · payment-initiation latency.

### Capacity method (honest)

Report capacity as **measured RPS at the first SLO breach**, with explicit assumptions (instance
count/size, DB tier, Redis tier, seat-map cache hit rate). Identify the **first bottleneck** (expected
candidates: DB connections under booking-heavy, Redis lock contention on a single hot show). Do not
extrapolate beyond the tested topology.

## P6.6 — Failure injection / chaos

**Gate: PENDING live run — scenario matrix + expected-invariant table provided.**

`scripts/chaos/inject.sh` toggles dependency failures against the staging stack (docker pause/kill,
`iptables`/toxiproxy latency, provider stub timeouts). For each, assert the invariant table:

| Injected failure                            | Expected behavior (assert)                                                             |
| ------------------------------------------- | -------------------------------------------------------------------------------------- |
| Redis unavailable / restart                 | Active booking **fails closed**; read APIs stay up; locks expire safely; no oversell.  |
| PostgreSQL unavailable / slow               | Writes fail closed; **no false confirmation**; recovery on reconnect.                  |
| Worker crash                                | Outbox/compensation backlog grows (observable); stale leases recover; no data loss.    |
| API crash                                   | LB routes to healthy replica; in-flight requests fail cleanly (idempotent retry safe). |
| Outbox dispatcher stopped / handler failure | Events pending, then re-driven; **exactly-once** handlers → no duplicate side effects. |
| Payment provider timeout / response lost    | Ambiguous → status recovery; **no double charge**; manual review if unknown.           |
| Provider booking timeout / response lost    | Never assumed confirmed; status query → retry/manual.                                  |
| Refund response lost                        | Status recovery; **no double refund**; manual review if unknown.                       |
| Object-storage / email failure              | Booking still confirms (side-effects retried/queued); no money impact.                 |
| Network latency / partial outage            | Circuit breaker trips; fail closed on the money path.                                  |

**Global success criteria (must hold across every scenario):** zero double-booking, zero
duplicate payment/refund, no false confirmation, no false refund, recovery works, backlogs observable,
manual-review paths activate, safe read APIs remain available.

The **DB-layer subset** of these invariants is already proven by the executed real-Postgres/Redis
concurrency suite + the P6.4 soak (0 double-finalize / 0 oversell). The **request-level + dependency-outage**
proofs require the staging stack and are PENDING.
