# P6.9 — Backup, Restore & Disaster Recovery

## Objectives (proposed — owner to ratify)

| Metric                  | Target                             | Rationale                                                            |
| ----------------------- | ---------------------------------- | -------------------------------------------------------------------- |
| **RPO** (max data loss) | ≤ 5 min                            | PostgreSQL is authoritative for all money/booking state; PITR + WAL. |
| **RTO** (max downtime)  | ≤ 60 min                           | Managed-PG restore + app redeploy from image.                        |
| Backup frequency        | Full daily + continuous WAL (PITR) | Standard managed-PG.                                                 |
| Retention               | 7 daily / 4 weekly / 3 monthly     | Adjust to compliance.                                                |
| Restore owner           | On-call SRE + DBA                  | Named in the incident contacts (P6.10).                              |

## What is authoritative vs reconstructable

- **PostgreSQL** — authoritative for bookings, payments, refunds, workflow, compensation, **outbox**,
  provider checkpoints, allocation accounting. Losing it = data loss up to RPO. **Primary backup target.**
- **Redis** — locks + BullMQ + cache. **Reconstructable, not authoritative.** On loss: locks expire
  (PostgreSQL held/confirmed accounting remains correct), queues recreate on worker boot (durable
  outbox re-drives domain events), cache repopulates. No PITR required; document expectations only.
- **Object storage** (tickets/QR/assets) — enable **versioning** + cross-region replication; regenerable
  from booking data if lost (QR is signed, deterministic).
- **Secrets** — stored in the platform secret manager; back up the manifest (names/rotation), never values.
- **Config / migrations** — in git; migrations are forward-only (no down-migrations → forward-fix).

## Restore rehearsal procedure (run where infra permits — otherwise these are the exact steps)

```bash
# 1. Provision a restore target (managed-PG PITR to a timestamp, or restore latest full+WAL).
# 2. Point a NON-production app stack at the restored DB (APP_ENV=STAGING).
# 3. Verify migration ledger + row-count sanity + a known booking/payment/refund reconciles.
DATABASE_URL=<restored> npx prisma migrate status            # expect "up to date"
DATABASE_URL=<restored> node scripts/soak/concurrency-soak.mjs --seconds 30   # invariants hold
# 4. Re-drive outbox: workers boot, FOR UPDATE SKIP LOCKED claims pending events (idempotent handlers).
# 5. Recreate BullMQ queues (automatic on worker start); confirm no duplicate side effects.
# 6. Provider checkpoints: inventory-sync resumes from persisted checkpoints (no replay storm).
```

**DR is NOT claimed proven until this rehearsal runs against a real restored database and the
invariant checks pass.** As of this report the rehearsal is **PENDING** (no managed-PG staging yet).

## DR runbook (per failure)

| Failure                    | Action                                                                                                                                                                     |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Database loss**          | Restore PITR to latest consistent point (≤ RPO); repoint apps; run restore rehearsal steps 3–6; resume traffic.                                                            |
| **Redis loss**             | No restore needed; redeploy Redis; locks expire safely; workers recreate queues; outbox re-drives. Read APIs stay up; **active booking fails closed** until Redis returns. |
| **Region failure**         | Fail over managed-PG replica + redeploy app images in the standby region; DNS/LB cutover; verify with soak.                                                                |
| **Worker outage**          | Backlog accumulates in outbox/compensation (observable via P6.7); scale workers back up; stale leases auto-recover. No data loss (durable).                                |
| **Queue loss**             | Recreate on worker boot; durable outbox is the source of truth, so events re-drive; idempotent handlers prevent duplication.                                               |
| **Payment webhook outage** | Provider retries; on recovery, signature-verified + idempotent pipeline dedupes; reconciliation/status-recovery closes gaps. No double financial action.                   |
| **Provider outage**        | Circuit breaker + provider-health signals; booking fails closed where it depends on the provider; read paths unaffected.                                                   |
