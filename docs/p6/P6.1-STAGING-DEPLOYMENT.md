# P6.1 — Staging Environment

Goal: a production-like, multi-instance staging deploy for the soak/chaos/load work in P6.4–P6.9.
**No production credentials. Mock/sandbox providers only. Money automation OFF.**

## Topology

`docker-compose.staging.yml` is an **overlay** on `docker-compose.prod.yml`:

```
             ┌──────────┐   ┌──────────┐
   clients → │  api #1  │   │  api #2  │      (--scale api=2, stateless, identical)
             └────┬─────┘   └────┬─────┘
                  └──────┬───────┘
        ┌────────────────┼────────────────┐
        ▼                ▼                 ▼
   PostgreSQL 16     Redis 7          (outbox lives in PostgreSQL)
   (authoritative)  (locks+queues)
        ▲                ▲
        └──────┬─────────┘
        ┌──────┴───────┐
   ┌────┴────┐   ┌─────┴────┐
   │worker #1│   │ worker #2│           (--scale worker=2, lease-based claims)
   └─────────┘   └──────────┘
```

Correctness under 2×API/2×worker comes from **PostgreSQL guarded writes + optimistic-concurrency
versions + Redis Lua fencing + FOR UPDATE SKIP LOCKED lease claims** — never instance affinity.

## Bring-up

```bash
# 1. Create .env.staging (git-ignored) with SANDBOX keys + secrets — NEVER inline in compose.
cp .env.example .env.staging   # then fill: JWT/*_SECRET, STRIPE_* (test), RAZORPAY_* (test), etc.

# 2. Start the multi-instance stack + observability
docker compose \
  -f docker-compose.prod.yml \
  -f docker-compose.staging.yml \
  -f docker-compose.observability.yml \
  up -d --scale api=2 --scale worker=2

# 3. Verify both API replicas answer health/readiness
for p in 4000 4001; do curl -fsS http://localhost:$p/api/health && echo " ok:$p"; done

# 4. Confirm safe defaults took effect (startup validation must NOT have been weakened)
docker compose logs api | grep -iE "APP_ENV=STAGING|compensation|refund|MANUAL_ONLY"
```

## Isolation guarantees (verified against code)

| Concern            | Status                                                                    |
| ------------------ | ------------------------------------------------------------------------- |
| Redis lock keys    | ✅ env-scoped by `APP_ENV` (`InventoryLockKeys` → `STAGING:lock:*`)       |
| Payment env        | ✅ `APP_ENV`-scoped; mock/test cannot promote to a live charge            |
| BullMQ queue names | ⚠️ **NOT** env-namespaced (`holds`, `inventory-sync-events`) — P6 backlog |
| CacheService keys  | ⚠️ **NOT** env-namespaced — P6 backlog                                    |

**Consequence:** staging MUST use its **own** Redis (this stack does). Do not point staging at a
production Redis until queue/cache keys are env-prefixed.

## Feature flags in staging (P6 policy — do not weaken)

Orchestrator `shadow`; provider confirmation OFF; allocated inventory OFF; compensation execution
OFF; auto-provider-cancel/void/refund OFF; `BOOKING_REFUND_POLICY_MODE=MANUAL_ONLY`; provider
`mock`. Enable individual behaviors ONLY inside a controlled soak/chaos run, never as the baseline.

## Cloud / managed staging (Railway / Azure / AWS) — when portal access exists

The compose is the reference topology. For managed platforms, translate 1:1:

- 2× API service replicas + 2× worker replicas behind the platform load balancer.
- 1× managed PostgreSQL (Flexible Server / RDS / Railway PG), 1× managed Redis **dedicated to
  staging**, 1× object-storage bucket (staging), 1× SMTP/sandbox email.
- Inject `.env.staging` values as platform secrets (never in the repo).
- Point Prometheus at every replica's `/api/metrics`; ship logs to the platform's central log sink.
- Health probe: `GET /api/health`; readiness gate the rollout on it.

**Blocked until:** authenticated cloud access + owner approval. No infrastructure is created by this
document. Where a portal is unavailable, the commands above are the exact executable substitute on
any Docker host.
