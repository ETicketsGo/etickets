# Production infrastructure readiness - October 2026

Prepared 2026-10-11 from the repository at `origin/main 6d9b4d1` and the owner's dated working
notes. No credential value appears here.

## How to read this

- **Nothing in this audit touched Railway, UAT or production.** There was no live inspection.
  Every "state" below is either read from code at the commit above (marked **code**) or taken from a
  dated observation made earlier by an engineer (marked **note, DATE**). A note is a photograph, not
  a current reading. Production has moved since several of them (it was 141-157 commits behind main
  on 2026-10-04). **Re-verify every "note" row against the live environment before relying on it.**
  The first command to run for most of them is named in the "Remediation" column.
- "Safe now" means: can be done or prepared in a non-production environment (or in the repository)
  without a deploy, a variable change or a credential change. "No" means it needs the owner, an
  external party, or a production change.

## Verdict

**Not ready to serve customers at scale. Safe to leave as it is.** The platform fails closed: it
cannot take a payment it cannot confirm, and the boot guards (managed secret store, no mock gateway,
no destructive seed) hold in code. The open items are configuration and external registrations, not
engineering. The three that matter most:

1. **The Razorpay webhook signing secret is unproven** and was proven wrong on 2026-10-06 (a real
   payment was captured and every delivery refused). Nothing outside a real signed delivery can
   confirm a fix.
2. **There is no demonstrably current, off-platform production backup**, and no restore has been
   rehearsed on production. A nightly job that is green proves nothing (it was green for five nights
   while taking no backup).
3. **No customer-facing message can be delivered in India** (no SMS, WhatsApp or push credentials,
   no DLT registration), and phone sign-in therefore cannot work. Email is the only channel.

## Order of work that unblocks production

1. Items 3-5 (backup you can read, off-platform copy, rehearsed restore). Nothing else should ship
   before a verified recovery point exists, because item 11 runs migrations.
2. Item 2 (webhook secret) and its alert, then a watched real payment to CONFIRMED.
3. Item 1 (secret store principal) so the readiness report is honest.
4. Items 6 and 12 (messaging) in parallel with 7 and 8 (KYC, Stripe), which are external lead times:
   start them first because everything else queues behind them.
5. Items 10, 13-17 as hardening before the first marketed launch.

## What this audit could not do

- Read live Railway state, logs, variables or backups (no access by design).
- Confirm any "note" row is still true today.
- Prove that webhook secrets, IAM permissions or DLT templates are correct; only a live signed
  delivery, a real `GetSecretValue` call and an operator-approved message can.
