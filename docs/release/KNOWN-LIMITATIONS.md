# ETicketsGo RC1 — Known Limitations

Accepted limitations for RC1, each with its risk, current mitigation, and recommended
follow-up. None is a go-live blocker for a controlled launch; several matter before
high-scale or specific-feature rollout. These are the audit items deliberately **not**
changed at RC (to avoid redesign / client-breaking changes), plus inherent platform bounds.

Severity reflects production impact, not effort.

| #   | Limitation                                                                                                                             | Risk / when it bites                                                                                                                               | Mitigation now                                                                                                                                                 | Recommended follow-up                                                                            |
| --- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 1   | **Rate limiting is per-instance** (in-memory throttler).                                                                               | With N API replicas the effective limit is N× per IP; brute-force/abuse protection dilutes as you scale out.                                       | Single-instance (or few) deployments are unaffected; auth limits are conservative.                                                                             | Back the throttler with the shared Redis (`REDIS_URL`), fail-open, before horizontal scaling.    |
| 2   | **API is unversioned** (served at `/api/*`, no `/v1`).                                                                                 | A future breaking contract change has no gradual-migration path for pinned clients (native/wallet/offline devices).                                | Contract is additive-only by convention; one client generation.                                                                                                | Adopt URI versioning (`/api/v1`) at the next major, or record an explicit "additive-only" ADR.   |
| 3   | **Production logs are not fully JSON**.                                                                                                | The default Nest logger wraps the structured request/error payloads, so log pipelines need light parsing to extract `correlationId`/`status`/`ms`. | Payloads are still emitted as JSON objects (parseable); correlation IDs exist; the worker already logs pure JSON.                                              | Configure a JSON logger (e.g. nestjs-pino) via `app.useLogger` in production.                    |
| 4   | **Audit rows rarely carry `correlationId`**.                                                                                           | Harder to join an audit entry to its request-log line during incident reconstruction.                                                              | The field is supported; auth + ops toggle now populate actor/IP; audit breadth is wide.                                                                        | Thread the request `correlationId` into `audit.record` at controller boundaries.                 |
| 5   | **Metric blind spots**: payout completion, wallet-pass issuance, and notification delivery success/failure have no dedicated counters. | No direct alerting signal if payouts stall or notifications silently fail.                                                                         | These flows are audited and log; adjacent metrics (payments, bookings, checkins, queue) are covered.                                                           | Add counters for payout completion and notification sent/failed.                                 |
| 6   | **Native Apple/Google wallet passes require real issuer credentials** (not shipped).                                                   | Wallet passes cannot be issued in production until credentials are configured.                                                                     | Fail-closed by design — providers report `unavailable` and no pass is issued without valid, non-placeholder credentials.                                       | Provision issuer certs/service accounts via the secret manager, then enable per provider.        |
| 7   | **Live payments are deployment-gated, not code-gated.**                                                                                | Real payments need external steps before they work.                                                                                                | `PAYMENT_LIVE_ENABLED=false` + mock force-disabled in prod; per-merchant certification + live-readiness gates.                                                 | Complete provider onboarding → ACTIVE merchant → PASS certification → readiness GO per provider. |
| 8   | **Deploy host step is a placeholder** in `deploy.yml`.                                                                                 | CI builds/pushes images and runs migrations, but the final rollout targets a specific host/orchestrator not wired here.                            | Build + migrate stages are real and gated by the full CI suite.                                                                                                | Wire the rollout step to the chosen host/registry/orchestrator.                                  |
| 9   | **Platform-role changes lag by the access-token TTL (~15 min).**                                                                       | A revoked platform role (ADMIN/SUPER_ADMIN) remains valid until the access token expires.                                                          | Org/tenant membership is checked live on every request (revokes immediately); short 15-min access TTL bounds the window; refresh-token reuse burns the family. | Accept for RC1 (conventional). If needed, add a token denylist / shorter TTL.                    |

## Explicitly out of scope for RC1 (by design)

- No architectural redesign or new platform capabilities (Phase 1 is feature-complete).
- Movies are catalogue-only where noted; enterprise capabilities are flag-gated off.
- Backup/restore is documented (managed-Postgres PITR + `pg_dump`); automated restore
  drills are a scheduled operational task, not an in-app feature.

## What is explicitly NOT limited (verified solid)

Secrets never reach the browser and fail closed in production; authorization/IDOR is
consistently enforced; QR/manifest signing + replay protection are sound; the offline gate
is server-authoritative and cannot convert a rejected scan to ACCEPTED; payments are atomic,
idempotent, and failover-protected; Redis outages degrade gracefully; migrations are
additive-only. See [RC-READINESS-REPORT.md](RC-READINESS-REPORT.md).
