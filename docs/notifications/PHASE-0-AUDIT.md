# Phase 0 — Notification platform audit

- **Branch:** `feat/provider-neutral-notifications` (no code changes made)
- **Date:** 2026-09-06
- **Baseline:** API suite green at **260 suites / 2551 tests**; the notification subtree alone is **16 suites / 142 tests**.
- **Purpose:** establish what already exists before anything is built, so that no parallel
  architecture is created next to working code.

## Headline

**This is not a greenfield.** A provider-neutral notification platform was decided and built in
ADR-020 and extended since. The channel seam, the transport seam, the registry, templates,
localization, per-user preferences, consent gating, scheduling and retry all exist, are wired into
DI, and are covered by tests. Real adapters exist for **SES, SendGrid, Twilio, Meta WhatsApp Cloud,
FCM, Expo and self-hosted VAPID** — they are not stubs.

Three things are genuinely wrong or missing, and only one of them is architectural:

1. **Provider selection is global, not per-market.** Each channel resolves exactly one transport
   from one env var (`EMAIL_PROVIDER`, `SMS_PROVIDER`, …) in a factory that runs once at module
   construction. "India → MSG91, USA/Canada → Twilio" cannot be expressed at all. This is the real
   gap, and the platform already contains the pattern to copy.
2. **Delivery is not isolated from the business transaction, and the row lies.** `send()` writes
   `status: 'SENT'` _before_ attempting delivery and does not catch delivery errors.
3. **SMS and WhatsApp cannot reach anyone.** Both read the recipient from `payload.phone`, which no
   caller sets — the identical defect already found and fixed for push.

MSG91 exists nowhere in the codebase; it appears once, in a table in `docs/notifications/PROVIDERS.md`.

## ADR conflicts

**None found.** ADR-020 explicitly anticipates this work: _"binding SendGrid/Twilio/FCM is a later,
isolated change"_. Per-market routing is an extension of its channel/transport seam, not a
replacement for it. ADR-037/040/041/042 govern inventory, sync, outbox and booking; none constrain
notification provider choice.

The one correction ADR-020 needs is factual: its "providers remain unimplemented (log-only)" line no
longer describes the code.

## Data-model changes: what is actually needed

This is the part you asked to see before it spreads. Graded honestly.

**Needed for the stated goal (2 nullable columns on an existing table, no new tables):**

| Change                                   | Why it cannot be avoided                                                                                                                                                                                         |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Notification.provider String?`          | Without it, nobody can answer "which provider carried this message" when a market's SMS stops arriving. With two SMS providers live at once, this is the difference between a five-minute diagnosis and a guess. |
| `Notification.providerMessageId String?` | The provider's own reference. It is what support quotes to MSG91/Twilio, and the only key any future delivery receipt could join on.                                                                             |

**Needed only if you want duplicate suppression (1 nullable column + 1 unique index):**

| Change                                   | Trade-off                                                                                             |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `Notification.dedupeKey String? @unique` | Cheap and contained. Skip it if you would rather accept occasional duplicate sends on caller retries. |

**Needed only if you want delivery receipts or bounce handling — NOT proposed:**

- A `NotificationDelivery` table (one row per attempt per provider).
- A `SuppressedDestination` table (hard bounces, complaints, STOP replies).

Both are real production concerns. Neither is required by "provider-neutral, country-routed
sending", and I am not proposing them in this mission. Say the word if you want either.

**Explicitly NOT needed, and NOT proposed:**

- No new provider/credential table — config already handles this correctly.
- No new preferences or consent model — the existing ones are correct.
- No changes to `Notification.status`, `attempts`, `lastError`, `locale`, `payload`, `readAt`.
- No template table — the code-based renderer with a build-time missing-key failure is better.
- No new queue — the worker's `dispatchDue` sweep already exists.

## Proposed work, in priority order

Nothing below has been started.

1. **Failure isolation + honest status** (no data-model change). Guard delivery; persist PENDING →
   SENT/FAILED. A provider outage must never fail a payment. Falsifying test: a throwing transport
   must not fail `confirmBooking`.
2. **SMS/WhatsApp recipient resolution** (no data-model change). Mirror `PushChannel`. Falsifying
   test: currently zero SMS reach a user with a stored phone.
3. **Per-market provider routing** — a `NotificationProviderResolver` modelled on
   `PaymentProviderResolver`: lazy construction, registry cache, and a pure routing function in
   `@eticketsgo/shared-types`. Config moves from `SMS_PROVIDER=twilio` to a per-market map, with the
   single-value form still honoured so nothing in QA/UAT breaks.
4. **MSG91 SMS + WhatsApp transports**, behind the existing interfaces, with DLT template ids in
   config. Log-only until real credentials exist — **no faked integration**.
5. **Notification metrics** on the existing `MetricsService`.
6. **The 2 nullable columns**, once 3 and 4 make them meaningful.
7. **ADR** superseding ADR-020's provider note.

## Open questions for you

1. **WhatsApp in US/Canada** — the Meta Cloud API adapter already exists and works in every market.
   Your brief says Twilio initially. Using what is already built is less code and one fewer vendor;
   Twilio is one account for both SMS and WhatsApp. Which?
2. **Delivery receipts** — in or out? It is the only item that would add a table.
3. **Which message types should actually go out over SMS/WhatsApp?** Today none do, and every SMS
   costs money. Once the recipient bug is fixed, whatever is on the default channel list starts
   sending for real.
