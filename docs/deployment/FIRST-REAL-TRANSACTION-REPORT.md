## 2. Root cause

`RAZORPAY_WEBHOOK_SECRET` on the PROD API does not match the secret set on the Razorpay
dashboard webhook.

The verification code is correct and is **not** the defect. Confirmed by inspection:

- `main.ts` creates the app with `rawBody: true`.
- The controller reads `req.rawBody` — the exact bytes Razorpay signed.
- `razorpay-payment.provider.ts:252` computes `HMAC-SHA256(secret, rawBody)` as hex and
  compares it timing-safely to `x-razorpay-signature`.

That is precisely Razorpay's documented algorithm. The inputs are right, so the only
remaining variable is the key — and the secret is provably present and non-empty, because
it is read with `requireKey` at provider construction and the same provider successfully
created the live order moments earlier. Config validation also enforces that it is distinct
from `RAZORPAY_KEY_SECRET`. It is set, and it is wrong.

**Likely origin.** This secret was generated by us and typed into the Razorpay dashboard by
hand, with our copy kept in `Documents/RAZORPAY_PROD_WEBHOOK.txt`. Razorpay never returns a
webhook secret, so the two sides could never be compared — a hand-entry mismatch (a typo, a
trailing newline or space, or a later regeneration on one side only) is the most likely cause.
Compare the dashboard value against that file, or simply set a fresh value in both places.

This failure mode was anticipated and written down in advance: the webhook signature was
recorded as the one link no check short of a real paid transaction could close, and a mismatch
was predicted to be silent and expensive. That prediction is now confirmed.

## 3. The escalation: the inventory was released

Ten minutes after the money was captured, the routine sweep expired the booking.

```
06:04:00Z  [worker] released expired holds { released: 1 }
```

The order was created 05:53:39Z and the hold window is 10 minutes
(`BOOKING_HOLD_MINUTES`, default 10), so the hold lapsed at ~06:03:39Z and the next sweep
tick at 06:04:00Z released exactly one hold. On a production environment with no other
traffic, that is this booking.

This follows directly from the code: `releaseExpiredHolds` selects on
`status: PENDING_PAYMENT` and an elapsed `holdExpiresAt`, **with no check on whether the
payment actually succeeded**. A payment that was captured but never reported is, to the
database, simply an unpaid booking. `expirePendingBooking` then writes `EXPIRED` and hands
the stock back.

The platform does have the right safety net for this exact situation — `payments.service.ts`
detects a capture against a booking that can no longer be paid and calls
`recordUnappliedCapture`, which writes a finance discrepancy and an audit entry for a person
to refund. **It never ran**, because it sits behind signature verification. The webhook was
rejected at the door, so not even the discrepancy was recorded.

Note: `expirePendingBooking` fails only payments in `REQUIRES_PAYMENT`. This payment was
`PROCESSING`, so the Payment row was left as-is. That is the detectable fingerprint of this
failure, and the existing read-only reconciliation report will classify it as `mismatched`
(ours not `SUCCEEDED`, provider `CAPTURED`).

## 4. This is not new — it predates today

The same rejection appears in the PROD logs before this purchase:

```
2026-10-04  06:52:08 / 06:58:48 / 07:01:26 / 18:52:08   400 PAYMENT_WEBHOOK_INVALID
```

The secret has been mismatched since the live webhook was configured. Today's purchase did
not cause the defect; it was the first delivery that carried real money, which is what made
it visible. **Any** live payment taken before this is fixed will fail the same way.

## 5. Owner actions required

1. **Align the webhook secret.** Set `RAZORPAY_WEBHOOK_SECRET` on the PROD API to the secret
   configured on the **live** Razorpay dashboard webhook for
   `POST /api/payments/webhooks/razorpay`. (Note the path: `payments/webhooks/razorpay`,
   plural `webhooks`.) Either read the live webhook's secret from the dashboard, or set a new
   one in both places.
2. **Then prove it** with a Razorpay dashboard test-event delivery returning 200, before any
   further real payment.
3. **Resolve this transaction as a business decision.** Rs 519.18 is captured, the booking is
   expired and the inventory is back on sale. The options are to refund the buyer or to
   honour the booking manually. No refund has been issued — the brief directed that it not be.
4. **Do not take further live payments** until step 2 passes.

Fixing the secret is time-sensitive for a second reason: if any retry is still outstanding,
a now-valid delivery would reach `recordUnappliedCapture` and convert this silent loss into a
properly recorded finance discrepancy. That outcome should be observed, not manufactured.
